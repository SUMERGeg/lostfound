# Удаление аккаунта

Статус: техническая политика Stage 4. Юридические сроки хранения и удаления из резервных копий должны быть утверждены владельцем сервиса; см. `owner-decisions-required.md`.

## Граница операции

`DELETE /api/v1/profile` требует действующий access token, текущий пароль и явное подтверждение. В одной транзакции сервис:

1. блокирует строку пользователя и проверяет пароль;
2. переводит аккаунт в `DELETED`, очищает идентифицирующие поля и увеличивает `auth_version`;
3. удаляет refresh-сессии, verification/reset tokens и email outbox пользователя;
4. удаляет пользовательский контент и приватные связи;
5. ставит каждый S3-объект в durable deletion queue;
6. фиксирует событие `ACCOUNT_DELETED` без email, телефона или других plaintext-данных.

После commit старые access/refresh tokens больше не работают. Ответ `202` содержит идентификатор операции и количество S3-объектов, поставленных в очередь.

## Матрица данных

| Данные | Действие в live-системе | Причина |
|---|---|---|
| `users` | статус `DELETED`; email, password hash, display name, phone, Telegram, MAX id и email verification очищаются | немедленно блокировать вход и убрать прямые идентификаторы |
| refresh/action tokens | физическое удаление | токены не нужны после прекращения аккаунта |
| auth email outbox | физическое удаление | payload содержит email/display name и не должен быть отправлен после удаления |
| объявления | статус `DELETED`; title/description/координаты/время/район очищаются | сохранить технический UUID для целостности аудита, убрать публичный и пользовательский контент |
| фото и upload metadata | DB-строки удаляются; object key переносится в очередь | URL/хэш/метаданные больше не нужны, S3 cleanup должен переживать сбои |
| secrets, owner questions/answers/contact snapshots | физическое удаление | содержат закрытые ответы и контакты |
| owner-checks, matches, feedback | связанные с аккаунтом записи удаляются | больше нет продуктового сценария, оправдывающего связь |
| notifications, chats/messages, legacy state/volunteer assignments | связанные записи удаляются | минимизация пользовательского контента и связей |
| reports пользователя/его объявлений | удаляются; `resolved_by` для остальных отчётов обнуляется | details могут содержать ПД; чужие отчёты сохраняются без связи с удалённым админом |
| consents | `withdrawn_at` заполняется, версия и время принятия остаются связаны только с необратимо обезличенным UUID | техническое доказательство версии и факта отзыва; срок хранения требует решения владельца |
| audit log | сохраняется с псевдонимным UUID; новое событие не содержит ПД | целостность security/admin аудита; срок хранения требует решения владельца |
| deletion job/object queue | сохраняются технические UUID, object keys и результат очистки | наблюдаемость, повтор и расследование ошибки cleanup |

## Object Storage и повторы

Worker выбирает объект с lease, вызывает идемпотентный S3 `DeleteObject`, затем помечает запись `DELETED`. При ошибке сохраняется сокращённое техническое сообщение, увеличивается счётчик и назначается экспоненциальная задержка до 60 минут. Зависший lease старше 10 минут может быть подобран повторно. Job становится `COMPLETED`, когда незавершённых объектов не осталось.

Удаление из CDN cache и резервных копий зависит от фактических провайдеров и их настроек. До production-выпуска владелец должен утвердить `[BACKUP_RETENTION]`, CDN invalidation и SLA удаления.

## Идемпотентность и ошибки

- S3 delete безопасно повторяется для уже отсутствующего ключа.
- DB-анонимизация выполняется только для `ACTIVE` аккаунта под row lock.
- Ошибка до commit оставляет аккаунт и очередь без частично применённых изменений.
- Ошибка Object Storage не возвращает данные в публичный API: объявление, фото-строки и аккаунт уже недоступны, а объект остаётся в retry queue.
