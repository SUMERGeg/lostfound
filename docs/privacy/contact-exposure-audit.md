# Аудит раскрытия контактов

Дата: 13 августа 2026 г.

## Текущая граница доступа

| Канал | Анонимный | Авторизованный посторонний | Участник owner-check | Admin |
|---|---:|---:|---:|---:|
| Email/phone/Telegram владельца в `/ads` | нет | нет | нет до approval; все заполненные каналы после approval | не через public/listing API |
| Display name/owner ID в `/ads` | нет | нет | ID известен из контекста проверки | email/ID в модерационных DTO |
| Exact coordinates | да | да | да | да |
| Public photo URL | да | да | да | да |
| Ответы owner-check | нет | нет | доступны участникам по текущей participant-проверке | отдельного admin API не найдено |

Положительная гарантия: публичные listing DTO не содержат прямых контактов или идентификатора автора. Контактный endpoint отделён и проверяет access token, verified email, участие и `APPROVED`.

## Недостатки

- Владелец не выбирает отдельно email, phone и Telegram: сохраняется snapshot всех заполненных полей.
- Перед approval нет явного экрана с перечнем конкретных значений и последствиями раскрытия.
- Нет срока действия, отзыва, повторного согласия при изменении контактов или события `CONTACT_DISCLOSED`.
- Snapshot остаётся после удаления аккаунта и не следует изменениям профиля.
- Exact coordinates и фото доступны ещё до любого owner-check; они сами могут косвенно идентифицировать владельца.
- Dormant legacy MAX flow умеет отправлять телефон волонтёру без этой границы; код не подключён в production, но должен быть удалён.

## Целевая модель

1. Владелец при создании/редактировании объявления выбирает разрешённые каналы раскрытия; default — ни одного.
2. Перед approval интерфейс показывает точные значения, получателя, причину и срок доступа.
3. Backend принимает только channel IDs, сам читает актуальные контакты и атомарно сохраняет consent/disclosure event; клиент не присылает произвольный номер/email как доверенное значение.
4. `GET contacts` возвращает пересечение: approved check ∩ выбранные каналы ∩ актуальный срок ∩ неотозванное согласие.
5. Изменение контакта не обновляет старый snapshot молча: нужен новый approval или явная политика.
6. Каждое первое чтение/раскрытие фиксируется минимизированным событием без самого контактного значения.
7. Account deletion отзывает доступ сразу и ставит snapshot на очистку по утверждённому retention.

## Контрактные тесты

- public list/detail никогда не содержат `author_id`, `email`, `phone`, `telegram`, `display_name`;
- неподтверждённый, посторонний и участник до approval получают deny;
- выдаются только выбранные каналы;
- revoked/expired disclosure недоступен;
- delete account немедленно закрывает endpoint и очищает snapshot по job;
- audit event не содержит контактное значение.

## Реализация Stage 3 — 13 августа 2026 г.

- Для `FOUND` объявления минимум один канал обязателен во frontend и backend; `LOST` объявления не используют owner-check disclosure.
- Разрешения хранятся отдельно в `listing_contact_preferences`; сами контактные значения там отсутствуют.
- Старые `FOUND` объявления после migration имеют безопасный default: разрешений нет. Перед следующим approval автор должен открыть редактирование и выбрать канал.
- При approval в `owner_check_contacts` попадает только пересечение выбранных каналов и актуально заполненных полей профиля.
- `GET /owner-checks/:id/contacts` по-прежнему требует verified authenticated participant и `APPROVED`; посторонний, pending или declined получает 403.
- Каждое успешное чтение пишет `CONTACT_DISCLOSED` с `actor_id`, owner-check, listing ID и названиями каналов. Email, телефон и Telegram в metadata не записываются.
- UI перед подтверждением показывает конкретные названия каналов и предупреждает о последствиях.
